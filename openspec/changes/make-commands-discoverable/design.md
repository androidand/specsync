# Design: couple the description to the code that runs it

## The problem to avoid

Separating "what a command is" (a registry or a metadata table) from "what a command does"
(a `run` function, a flag set, a `switch` case) recreates the drift this change exists to
remove. They describe the same thing, so they must be one thing.

## The idiom: one type per command, implementing one interface

Go's own tooling already solves this. The `go` command defines a `Command` type with its
usage line, short and long descriptions, flag set and `Run` in one value; `go help` is
generated from those values, and the checked-in `alldocs.go` is regenerated by a script and
verified by a test. specsync keeps the same shape using only the standard library (it has no
third-party dependencies and should keep it).

```go
// A Command is everything specsync knows about one subcommand.
type Command interface {
    Spec() Spec                                       // identity and documentation
    Flags(fs *flag.FlagSet)                           // define flags, bound to the receiver
    Run(ctx context.Context, args []string) error     // do the work
}

type Spec struct {
    Name     string
    Group    Group      // typed constant: a typo does not compile
    Summary  string     // one line
    Intents  []string   // phrases a person would use ("what is the state of my work")
    Mutates  bool
    Workflow Workflow
    Safety   []string
    Examples []string   // full command lines
}
```

Each command is one file with one type that holds its flag values as fields:

```go
type statusCmd struct{ root multiFlag; epic string; json bool }

func (*statusCmd) Spec() Spec { return Spec{Name: "status", Group: GroupOverview, /* ... */} }
func (c *statusCmd) Flags(fs *flag.FlagSet) {
    fs.Var(&c.root, "root", "workspace directory to search for clones (repeatable)")
    fs.StringVar(&c.epic, "epic", "", "roll up everything under this epic")
    fs.BoolVar(&c.json, "json", false, "emit machine-readable output")
}
func (c *statusCmd) Run(ctx context.Context, args []string) error { /* ... */ }

func init() { Register(&statusCmd{}) }
```

## Why this closes the gap

- **There is no separate `run` to forget to wire.** The only way into a command's logic is
  through its declaration, because the logic is its `Run` method. A command cannot exist
  without being dispatchable, and cannot be dispatched without being declared. The current
  `switch` and `knownSubcommands` disappear, and an unreferenced helper is caught by the
  linter's unused-code check instead of an allowlist.
- **Flags are declared once and read twice.** `Flags(fs)` defines the flags that `Run`
  reads. `agent-help` builds a fresh `flag.FlagSet`, calls `Flags`, and reads names, types,
  defaults and usage with `VisitAll`. The hand-written flag lists go away.
- **Registration is automatic.** `Register` is called from `init()` in the command's own
  file, the same idiom as `database/sql` drivers. A file that compiles is registered; there
  is no central list to edit and forget. Output order is by group then name, so `init()`
  order never shows.
- **An incomplete declaration cannot start.** `Register` validates the Spec and panics on an
  empty summary, group or examples, an undeclared group, a duplicate name, or any flag
  without usage text, the way `flag` panics on a duplicate flag and `http.Handle` on a
  duplicate pattern. The first test run, and any run of the binary, fails loudly. Nothing
  incomplete can ship.
- **Examples cannot rot.** A test parses every example's flags against the command's own
  flag set, so an example naming a flag that no longer exists fails.
- **Everything else is a view.** The overview, `agent-help`, the task index, the README
  command table and the skill are rendered from the registered commands. Generated files
  are checked in and regenerated with `go generate`; a test (the same pattern as the `go`
  command's `alldocs.go`) fails when the committed copy differs from a fresh render.

## The one parity test

A single table-driven test is the keystone that keeps every visible surface honest. It reads
what each surface actually shows (it does not trust the generator) and compares it, in both
directions, with the registered commands.

```go
func TestEverySurfaceListsExactlyTheRegisteredCommands(t *testing.T) {
    want := registeredNames()                       // the single source of truth

    surfaces := map[string]func(t *testing.T) []string{
        "help overview":      namesFromHelpOutput,        // run the real help renderer
        "agent-help list":    namesFromAgentHelpList,
        "agent-help -json":   namesFromAgentHelpJSON,
        "README table":       namesFromMarkedSection("README.md"),
        "skill (canonical)":  namesFromMarkedSection("skills/specsync/SKILL.md"),
        "skill (each copy)":  namesFromEachDerivedSkill,  // every harness copy
        "dispatch":           namesThatDispatch,          // each registered name runs; an unregistered word does not
    }

    for surface, got := range surfaces {
        t.Run(surface, func(t *testing.T) {
            missing, extra := diff(want, got(t))
            if len(missing)+len(extra) > 0 {
                t.Fatalf("%s is out of step\n  missing: %v\n  not a command: %v\n"+
                    "fix: declare the command once (Spec) and run `go generate`", surface, missing, extra)
            }
        })
    }
}
```

- **Both directions.** A command that is registered but not shown is `missing`; a surface
  that names something that is not registered, such as a removed command still in the README,
  is `extra`.
- **One line to add a surface.** A new place that lists commands (a new harness, a man page)
  adds one entry to the map, and from then on cannot drift.
- **Independent of the generator.** It parses the committed files, so it also catches "forgot
  to run `go generate`".
- **Failure tells you what to do.** The message names the surface, the commands, and the fix.
- **Acceptance criterion.** Written first, against today's code, it must fail naming
  `topology` (absent from `agent-help`, the README and the skill) and `relate` (implemented
  but not dispatchable). It is green only when the gap is closed.

### The same test forces the refactor

Checking surfaces after the fact is not enough while a second list can still be written. The
test therefore also has a source-level entry: it parses the non-test Go files of the command
package with `go/parser` and fails when a hand-kept list of command names exists outside the
command declarations, meaning a composite literal (map or slice) or a `switch` with three or
more case labels whose string constants are registered command names. The declarations
themselves are exempt because a declaration holds exactly one name.

```go
"source: no second list of commands": namesInHandKeptLists, // must be empty
```

Against today's code this fails on `knownSubcommands`, the dispatch `switch`, the keys of
`commandMetadata` and the `knownConfusions` table, each reported with file and line. The only
way to turn it green is to do the refactor: dispatch and documentation derive from the
declarations, and anything else that needs a command name (for example the habit-word
suggestions) becomes a field of the command's `Spec`, such as `Confusions`. It also keeps
working afterwards: a hand-kept list that reappears makes the test fail again, with the file
and line to fix.

The migration is test-driven by construction. The test is written first and red; each ported
command removes failures; deleting the last duplicate list makes it green.

This test checks *membership*. Freshness of the generated text is checked separately by the
CI step that regenerates the docs and fails on any difference.

## Alternatives considered

- **A metadata table or registry file separate from the commands** (the current
  `commandMetadata`, or YAML/JSON next to the code). Rejected: it is the separation this
  change removes.
- **A command framework such as cobra.** It offers the same coupling and doc generation, but
  adds a dependency and a different flag package to a project that has none. The standard
  `flag` package plus a thin interface gives the same property.
- **Explicit list of commands in one file** (`var commands = []Command{...}`). Rejected as
  the primary mechanism: forgetting to add an entry is exactly the failure; `init()`
  registration cannot be forgotten.
- **Structured comments or struct tags scanned by a generator.** Rejected: a second source
  of truth that the compiler does not check.
- **Struct with function fields instead of an interface.** Equivalent. An interface is
  preferred because a missing method is a compile error and a command's flag values can live
  on the receiver instead of closures.

## Where the code lives

Declarations live in `cmd/specsync`, next to flag parsing and output, because they describe
the command line. The core logic stays in the library package and is called from `Run`, so
the library's public surface is unchanged.

## Migration

1. Introduce `Command`, `Spec`, `Register` and the validation, with a test that today's
   golden `agent-help` output is reproduced.
2. Port commands one at a time; the old `switch` falls back for any command not yet ported,
   so the tool works at every step.
3. When the last command is ported, delete the `switch`, `knownSubcommands` and
   `commandMetadata`.

## Risks

- **`init()` registration is implicit.** Mitigated by validation at registration and a test
  that lists every registered command; the registered set is also visible in `help`.
- **A large mechanical migration.** Mitigated by the golden snapshot and one command per
  step.
- **Package-level state.** Registration mutates a package variable at init; it is
  write-once before `main` and read-only afterwards.
