- [ ] `openspec view` ignores a declared store: run from a code repo whose `openspec/config.yaml` says `store: <id>` and it reports "0 specs, 0 changes" and exits 0, while `list`, `status` and `validate` all resolve the store correctly. It also rejects `--store`. The one command that presents itself as the dashboard is the one that silently shows an empty one
- [ ] Validator only recognises SHALL/MUST on a requirement's first body line. A requirement whose normative verb wraps to line two fails with "must contain SHALL or MUST", which reads as though the word is absent. Either scan the whole requirement body or say which line was checked
- [ ] Archive leaves `## Purpose\nTBD - created by archiving change <slug>. Update Purpose after archive.` and nothing ever prompts again. 16 of 18 capabilities in this repo still carried the placeholder months later. Either prompt on archive or omit the placeholder so the gap is visible
- [ ] Propose a standard target-repository field on a change. Store docs describe changes as location-agnostic, but a change in a shared store must name the code repo it targets or every tracker-sync tool invents its own. specsync is shipping `targets` in a committed per-change `specsync.yml`; happy to converge on whatever shape upstream prefers
- [ ] `openspec validate` fails any change with no `specs/` delta ("Change must have at least one delta"). That makes a coordination or chore change unrepresentable, and pushes people either to invent a hollow requirement or to stop using changes for that work. A change with no behaviour delta is a legitimate shape; warn rather than fail, or let a schema opt out
